# Device Simulator Protocol

## 1. Purpose

This document defines the HTTP contract between the Water Quality Monitoring application and the supplied device simulator. The simulator is an independently operated external system. Implementations should rely on this contract rather than assumptions about its internals.

## 2. Flow

```text
Operator requests a measurement
            ↓
Application sends a command to the simulator
            ↓
Simulator acknowledges the command
            ↓
Simulator performs the measurement
            ↓
Simulator POSTs a result to the callback URL
            ↓
Application acknowledges the callback
```

A command acknowledgement confirms receipt. It does not guarantee that the physical measurement will complete successfully.

## 3. Simulator service

Default base URL:

```text
http://localhost:9000
```

Endpoints:

```text
GET  /health
GET  /api/devices
POST /api/devices/{device_id}/measurements
```

The OpenAPI interface is available at `/docs`.

## 4. Devices

`GET /api/devices` returns the available device identifiers, names, and sites. Device identifiers are case-sensitive.

## 5. Measurement command

```http
POST /api/devices/device-001/measurements
Content-Type: application/json
```

```json
{
  "request_id": "req-4c7f12a8",
  "requested_at": "2026-07-11T03:15:00Z",
  "callback_url": "http://host.docker.internal:8000/api/device-results",
  "parameters": [
    "ph",
    "temperature_c",
    "turbidity_ntu",
    "dissolved_oxygen_mg_l"
  ]
}
```

| Field | Required | Description |
|---|---:|---|
| `request_id` | Yes | Unique identifier generated by the application. Reuse it when retrying the same logical request. |
| `requested_at` | Yes | ISO 8601 timestamp indicating when the command was created. |
| `callback_url` | Yes | HTTP or HTTPS endpoint to which the simulator will send the eventual result. |
| `parameters` | Yes | Non-empty list of supported measurement parameters. |

Supported parameters:

- `ph`
- `temperature_c`
- `turbidity_ntu`
- `dissolved_oxygen_mg_l`

## 6. Synchronous acknowledgement

### Accepted

```http
HTTP/1.1 202 Accepted
```

```json
{
  "request_id": "req-4c7f12a8",
  "device_id": "device-001",
  "status": "accepted",
  "acknowledged_at": "2026-07-11T03:15:01Z"
}
```

### Already accepted

A repeated command using the same `request_id` and device may return:

```http
HTTP/1.1 200 OK
```

```json
{
  "request_id": "req-4c7f12a8",
  "device_id": "device-001",
  "status": "already_accepted",
  "acknowledged_at": "2026-07-11T03:15:01Z"
}
```

This is a successful idempotent acknowledgement and does not create a second logical measurement.

### Busy

```http
HTTP/1.1 409 Conflict
Retry-After: 5
```

```json
{
  "request_id": "req-4c7f12a8",
  "device_id": "device-001",
  "status": "busy",
  "retry_after_seconds": 5
}
```

The same logical command may be retried later with the same `request_id`.

### Temporary unavailability

```http
HTTP/1.1 503 Service Unavailable
Retry-After: 10
```

```json
{
  "request_id": "req-4c7f12a8",
  "device_id": "device-001",
  "status": "retry",
  "error_code": "TEMPORARILY_UNAVAILABLE",
  "message": "The device service is temporarily unavailable."
}
```

### Permanent rejection

Unknown devices, unsupported parameters, malformed requests, or conflicting reuse of a request identifier may return a `4xx` response with `status: rejected`. A permanent rejection should not be retried without correcting its cause.

## 7. Successful result callback

After an accepted command, the simulator may later POST the following to the supplied `callback_url`:

```json
{
  "request_id": "req-4c7f12a8",
  "event_id": "evt-92a28df1",
  "device_id": "device-001",
  "status": "completed",
  "recorded_at": "2026-07-11T03:15:05Z",
  "sequence_number": 1842,
  "readings": {
    "ph": 7.18,
    "temperature_c": 27.4,
    "turbidity_ntu": 1.6,
    "dissolved_oxygen_mg_l": 6.2
  }
}
```

`request_id` correlates the result to the originating command. `event_id` identifies the callback event and remains unchanged if callback delivery is retried. `sequence_number` is local to the device and should not be assumed to arrive in strict order.

## 8. Failed result callback

A device may acknowledge a command and subsequently fail:

```json
{
  "request_id": "req-4c7f12a8",
  "event_id": "evt-92a28df1",
  "device_id": "device-001",
  "status": "failed",
  "sequence_number": 1842,
  "error_code": "SENSOR_TIMEOUT",
  "message": "A sensor did not respond before the measurement deadline."
}
```

The set of device error codes is not guaranteed to be exhaustive.

## 9. Callback acknowledgement

The application should acknowledge callbacks only after the result has been processed or durably persisted.

New event:

```http
HTTP/1.1 200 OK
Content-Type: application/json
```

```json
{
  "event_id": "evt-92a28df1",
  "status": "received"
}
```

Repeated event:

```json
{
  "event_id": "evt-92a28df1",
  "status": "already_received"
}
```

The simulator treats `200`, `201`, `202`, and `204` as successful callback delivery. A `422` response is treated as a permanent rejection. Network failures and selected temporary status codes may cause the callback to be delivered again using the same `event_id`.

## 10. Delivery and ordering

The protocol provides at-least-once delivery rather than exactly-once delivery. Applications should therefore expect that:

- commands may be retried;
- callbacks may be repeated;
- results may complete in a different order from the commands;
- an acknowledged command may complete, fail, be delayed, or never produce a callback;
- values may be outside expected ranges while still being structurally valid readings;
- input from an external device may occasionally be incomplete or unexpected.

The application should use `request_id` and `event_id` for correlation and idempotency rather than relying on arrival order.

## 11. Expected operating ranges

| Parameter | Minimum | Maximum |
|---|---:|---:|
| pH | 6.5 | 8.5 |
| Temperature | 0 °C | 40 °C |
| Turbidity | 0 NTU | 5 NTU |
| Dissolved oxygen | 4 mg/L | 12 mg/L |

A numeric value outside these ranges is an abnormal measurement, not necessarily an invalid protocol message.

## 12. Scope

Authentication is outside the required scope of the technical assessment. The contract does not prescribe the application's data model, frontend framework, retry policy, timeout policy, alert model, or internal architecture.
